## Executive Summary

I built the Flashcard Quizzer, a command-line application that helps new hires
memorize terms such as server acronyms. It loads flashcards from a JSON file,
asks them in the terminal, compares answers case-insensitively, gives colored
feedback and ends with a summary table of total questions, accuracy and missed
terms.

The application has three quiz modes (sequential, random and adaptive),
implemented with the Strategy and Factory patterns. The adaptive mode uses a
persistent history to ask previously missed cards first and repeats missed
cards during a session. Further features are `--stats`, `--export`, a question
limit, reproducible shuffling and graceful exit via `exit` or Ctrl+C.

All code was generated by Claude Code. My role was to break the specification
into prompts, review every result with automated tools, manual runs and tests,
and send the agent back when something was wrong. Eight concrete review
findings are documented in `docs/ai_edit_log.md`.

## Project Overview

### Problem Statement
A startup needs a lightweight internal tool for new hires to memorize
acronyms. It must run in the terminal, read decks from JSON, offer different
quiz modes and be clean enough to extend later.

### Solution Approach
- **Separation of concerns:** loading (`data_loader.py`), quiz logic
  (`quiz_engine.py`), terminal I/O (`ui.py`), persistence (`history.py`),
  wiring (`cli.py`) and shared data classes (`models.py`).
- **No I/O in the logic:** `QuizSession` only scores answers, and `ConsoleUI`
  takes injectable input/output streams. This made a full integration test
  with a simulated user possible without a real terminal.
- **Technology:** Python 3.12, `argparse`, `dataclasses`, `colorama` as the
  only runtime dependency, pytest, black, isort, flake8 and mypy.

### Final Features
- [x] Load decks in array or `{"cards": [...]}` format with validation
- [x] Friendly one-line errors instead of tracebacks
- [x] Sequential, random and adaptive quiz modes
- [x] Session summary with accuracy and missed terms
- [x] Persistent history across sessions and `--stats`
- [x] JSON export of the session summary (`--export`)
- [x] Question limit (`-n`), reproducible order (`--seed`), `--no-color`

### Most Valuable AI Interactions

#### Example 1: Strategy and Factory in `quiz_engine.py`
**Context:** Core requirement of the project.
**AI Prompt:** An abstract `QuizMode` with `next_card()` and a
`record_result()` hook, three subclasses and a factory.
**AI Response:** A clean implementation; the hook lets the adaptive mode react
to answers while the other modes ignore them.
**Your Changes:** Only the adaptive sort order (Example 3).
**Outcome:** Adding a spaced-repetition mode means one new class and one line
in the factory.

#### Example 2: Corrupt history file
**Context:** Error-handling review of `history.py`.
**AI Prompt:** "Check the error handling of `HistoryStore` for malformed
history files."
**AI Response:** Validation in `load()`.
**Your Changes:** I rejected the fix as incomplete. The CLI continues after the
warning and later calls `record()`, which still crashed on the same file. Both
methods now share one validation.
**Outcome:** A broken history file produces warnings, never a traceback.

#### Example 3: Adaptive order
**Context:** Manual run of two adaptive sessions.
**AI Prompt:** "Order by past miss rate."
**AI Response:** Sort by miss rate, worst first.
**Your Changes:** Never-seen cards have a miss rate of 0, like mastered cards,
so known cards came before new ones. The order is now missed → new →
mastered.
**Outcome:** Behavior that actually supports learning, covered by a new test.

### Challenges with AI Collaboration
- **Consequences across modules:** the AI fixed the place I pointed to, not the
  second code path that used the same data.
- **Literal interpretation:** "order by miss rate" was implemented exactly,
  including its unhelpful edge case.
- **Too literal tests:** assertions depended on table padding and broke when a
  value got wider.
- **Environment surprises:** Windows-invalid file names in the starter
  repository, and isort rewriting starter files.

## Software Engineering Practices

### Code Quality Measures
- [x] Code formatting (black, isort)
- [x] Linting (flake8, mypy in strict mode)
- [x] Type hints on every function, including tests
- [x] Docstrings on all public classes and functions
- [x] Error handling with custom exceptions (`FlashcardLoadError`,
  `JsonFileError`)

### Testing Strategy
91 pytest tests with 99 % line coverage. They cover unit tests per module,
twelve malformed deck structures, corrupt history files, write failures and
full CLI runs with a simulated user (including Ctrl+C and end of input). All
file access uses temporary folders. I did not use strict test-driven
development. Tests were generated after the first manual run, and that run
found the adaptive-order issue.

### Design Patterns Used
- **Strategy:** `QuizMode` with `SequentialMode`, `RandomMode` and
  `AdaptiveMode`. I chose it because the modes are different algorithms for
  one task: choosing the next card. `QuizSession` never needs to know which
  one it runs.
- **Factory:** `create_quiz_mode()` maps the `--mode` flag to a strategy and
  passes each mode only what it needs (history for adaptive, a random
  generator for random). The CLI therefore has no mode-specific code.

### Code Structure and Organization
Each module has one responsibility. I removed the starter's `TaskManager` and
`FileHandler`: they were unused, and `FileHandler` returned `{}` for missing
files, which contradicts the error-handling requirement. The folder structure
was kept.

## Technical Challenges and Solutions

### Challenge 1: Graceful failure everywhere
**Problem:** Missing files, invalid JSON, permission and encoding errors all
raise different exceptions.
**Solution:** `utils/file_handler.py` translates them into one `JsonFileError`
with a readable message (including line and column for JSON errors).
`cli.py` prints it and exits with code 1.
**AI Involvement:** Generated by the AI; review added the corrupt-history case.
**Lessons Learned:** Centralizing error translation keeps messages consistent.

### Challenge 2: Testing an interactive program
**Problem:** The quiz reads from the keyboard.
**Solution:** Injectable `input_func` and output streams; `scripted_input()`
simulates a user and raises `EOFError` when the answers run out.
**AI Involvement:** Suggested by the AI after I required tests without real
terminal input.
**Lessons Learned:** Designing for testability up front is cheaper than
mocking later.
